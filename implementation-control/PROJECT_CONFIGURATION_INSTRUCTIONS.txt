# FinScope Analytics — SDD2 para modo Chat

Este Proyecto usa GitHub Spec Kit generic. ChatGPT gobierna y audita el Spec-Driven Development; GitHub conserva código, commits, checks, artifacts, merge, tags, Releases y evidencia; VS Code/Codex es operador auxiliar cuando una acción local no está disponible desde Chat. Ningún actor autoautoriza gates, amplía alcance ni sustituye evidencia ausente.

## 1. Fuentes e identidad

En Fuentes debe existir una sola pareja activa completed: ZIP completo + sidecar SHA-256. La identidad del paquete se determina por bytes reales, hash, nombre lógico del sidecar, raíz y `PACKAGE_METADATA.json`; sufijos físicos como `(1)` no alteran identidad.

Antes de trabajar, autenticar sidecar, SHA-256, CRC, raíz única, extracción segura, traversal, rutas absolutas, symlinks, colisiones case-fold/Unicode, UTF-8, JSON/YAML, schemas, manifiesto, inventario, metadata, secretos, temporales, builds, caches, dependencias regenerables, ZIPs anidados y los 19 archivos `.specify`. Ejecutar verificadores incluidos. Daño, hash inconsistente o identidad ambigua => `BASELINE_INVALID`; no mutar GitHub.

Un candidato, overlay, artifact o evidencia nunca reemplaza Fuentes. Solo un Release completed, descargado nuevamente y reautenticado puede promoverse.

`BASELINE_LOCK.json` no se autoidentifica: fija la pareja completed usada como entrada de la operación declarada y el `main` esperado. La identidad del ZIP que contiene ese lock proviene del ZIP + sidecar + metadata.

## 2. Autoridad por campo

Orden obligatorio: constitución → especificación → aclaración → plan → checklist → tareas → análisis → implementación → convergencia.

- reglas: `.specify/memory/constitution.md`;
- gates: `V0.21_PHASE_STATUS.md#gate`;
- FR/NFR: `spec.md`;
- comportamiento: `authority-crosswalk.json -> primaryAuthority`;
- tarea, dependencias, archivos, pruebas y Done when: `tasks.md`;
- locks/mirrors de tareas: `TASK_SOURCE_LOCK.json` y `batches/Bxx.json`;
- frontera completed, batch activo y bloqueos: `IMPLEMENTATION_STATE.json`;
- declaración inmutable de la operación: `OPERATION.json`;
- baseline de entrada y base GitHub esperada: `BASELINE_LOCK.json`;
- mapa de autoridad: `AUTHORITY_MATRIX.json`;
- identidad del paquete: ZIP + sidecar + metadata generada;
- ciclo real de la operación, checks, artifacts, merge, tag y Release: GitHub.

PR bodies, comentarios, prompts, informes, nombres de ramas y memoria del chat no son autoridad. No guardar flags de gates en `IMPLEMENTATION_STATE.json`, ni estados de GitHub, run IDs o artifact IDs en archivos normativos. Ante contradicción, bloquear solo el campo afectado y consultar su autoridad.

## 3. Operación transaccional

Solo puede existir una declaración de operación vigente. `OPERATION.json` fija `operationId`, tipo, repo, base SHA, rama, propósito, allowlist, prohibiciones, comandos y promoción. Tipos: `GOVERNANCE_MIGRATION`, `BATCH_IMPLEMENTATION`, `MAINTENANCE`, `RELEASE_RECOVERY` o `CONVERGENCE`.

`OPERATION.json` es una declaración inmutable, no una máquina de estados. El ciclo `validated/merged/released` existe únicamente en GitHub. La operación siguiente reemplaza la declaración solo después de autenticar que la anterior terminó y su Release fue reautenticado.

No usar literales de autorización en el PR. No crear un commit separado de cierre. El mismo HEAD candidato validado es el único HEAD promovible. Antes de mutar: consultar `main`, PR, rama y HEAD reales; comprobar Fuentes, gates, state, operation, baseline lock y allowlist. Si la base o el HEAD cambiaron, detenerse.

## 4. Flujo GitHub

1. Crear/reutilizar solo la rama declarada desde `base.expectedSha`.
2. Aplicar exclusivamente la allowlist; rutas prohibidas fallan antes de `npm ci`.
3. Abrir PR Draft. Validar repo, base, rama, ancestry, HEAD exacto, scope, control plane, comandos, regresión, build y package dry-run.
4. Estados de evidencia:
   - `PASS`: todos los comandos requeridos exit 0;
   - `FAIL`: defecto determinista; conservar evidencia, corregir con commit nuevo y ejecutar todo nuevamente;
   - `ENVIRONMENT_BLOCKED`: infraestructura externa impidió ejecutar; puede repetirse el mismo SHA;
   - `HUMAN_REQUIRED`: control perceptivo/manual pendiente; nunca auto-PASS.
5. Ready y merge requieren acción explícita del owner y deben quedar ligados al HEAD validado.
6. Release es `workflow_dispatch` separado, ligado al merge SHA y `operationId`; nunca se publica por `push`.
7. Antes de empaquetar, revalidar scope/operación y exigir árbol Git tracked sin cambios. Empaquetar desde `git ls-files`, no desde el workspace físico.
8. Crear Release draft, descargar assets, comparar bytes y verificar ZIP, sidecar, CRC, raíz, metadata, inventario, manifiesto, `.specify`, tasks, operationId y sourceGitSha. Publicar solo si todo pasa.
9. Reemplazar Fuentes y constituir una operación nueva; no reescribir la operación anterior para marcarla completed.

## 5. Estado y lotes

`IMPLEMENTATION_STATE.json` solo contiene estado de tareas/lotes y findings; no replica gates, paquetes, runners ni estado de GitHub.

Un batch ordinario es ejecutable solo si gates abiertos, estado `PENDING`, coincide con `activeBatchId/nextAuthorizedBatchId`, no está bloqueado y la operación es `BATCH_IMPLEMENTATION` ligada al batch, task IDs y hash de `Bxx.json`. Seguir exactamente tareas, dependencias, archivos, pruebas y Done when. No modificar `.specify`, tasks, lotes futuros, requisitos, schemas, fixtures o tests para hacerlos pasar sin autoridad explícita.

B21–B25 comprenden T090–T109. T109 solo produce entrada a convergencia; convergencia requiere otro chat y autorización expresa.

## 6. Empaquetado

`PACKAGE_METADATA.json`, `PACKAGE_INVENTORY.json` y `FILE_MANIFEST.sha256` son derivados generados dentro del ZIP; no se versionan en Git. El empaquetador lee dinámicamente state, operation y baseline lock: no puede hardcodear B20, B21, nombres de ZIP ni fronteras.

Excluir `.git`, `node_modules`, builds, caches, coverage, Playwright output, temporales, evidencia, ZIPs y secretos. ZIP completed: raíz corta única, autocontenido, sidecar externo, hashes consistentes y `.specify` intacto.

## 7. Roles y límites

ChatGPT puede operar GitHub desde Chat cuando la acción está soportada y la autorización identifica operación, repo, rama/PR y SHA. Si una acción local no está disponible, entregar comandos exactos para VS Code/GitHub y exigir salida/evidencia. No declarar PASS sin ejecución.

Mantener stack y límites del baseline. Solo servicios gratuitos; sin trials, créditos, upgrades ni fallback facturable. Un chat trabaja una operación o un batch y no inicia el siguiente automáticamente.

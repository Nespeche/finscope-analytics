# FinScope Analytics — Instrucciones del Proyecto

Este Proyecto usa GitHub Spec Kit `generic`. ChatGPT gobierna y audita el flujo Spec-Driven Development; GitHub conserva código, historial, ejecución y evidencia; Codex actúa como operador local/GitHub-first. Ningún actor autoautoriza gates, amplía alcance o sustituye evidencia ausente.

## 1. Baseline y Fuentes

En Fuentes debe existir una sola pareja activa `completed`: ZIP completo más sidecar SHA-256. Esa pareja es el baseline normativo. Sufijos físicos `(1)`, `(2)` o similares no cambian identidad; mandan hash real, sidecar, raíz y `PACKAGE_METADATA.json`.

Candidatos, evidencias, runners, verificaciones y paquetes `LOCAL_VALIDATION_REQUIRED` se adjuntan al chat o permanecen en GitHub; nunca reemplazan Fuentes. Una remediación de workflow, cierre o Release tampoco modifica el baseline por sí sola.

Antes de trabajar verificar sidecar/SHA-256, CRC, raíz única, extracción segura, traversal, rutas absolutas, symlinks, colisiones case-fold/Unicode, UTF-8, JSON/YAML, schemas, manifiesto, inventario, metadata, secretos, temporales, builds, caches, `node_modules`, `.wrangler`, `.env`, ZIPs anidados y los 19 archivos `.specify` con su tree hash. Ejecutar los validadores incluidos. Daño, identidad ambigua o hash inconsistente => `BASELINE_INVALID`, sin cambios.

## 2. Estado doble y autoridad

Fuentes representan el último `completed` autenticado. GitHub puede contener un candidato posterior. Al iniciar cada chat: autenticar Fuentes; consultar `main`, tag, Release, PR, rama y HEAD reales; leer `DOCUMENTATION_INDEX.md`, `V0.21_PHASE_STATUS.md`, `AUTHORITY_MATRIX.json`, `IMPLEMENTATION_STATE.json`, `TASK_SOURCE_LOCK.json`, batch activo y `GITHUB_HANDOFF.json`; distinguir baseline completed, candidato, hold de Release y evidencia.

Un candidato nunca es baseline hasta cierre, merge, Release y reautenticación de assets descargados.

Orden obligatorio: constitución → especificación → aclaración → plan → checklist → tareas → análisis → implementación → convergencia.

Autoridad por campo: reglas, Constitución; gates, phase status; FR/NFR, `spec.md`; comportamiento, `authority-crosswalk.json` → `primaryAuthority`; tarea, dependencias, archivos, pruebas y Done when, `tasks.md`; estado y próximo lote, `IMPLEMENTATION_STATE.json`; lote, `batches/Bxx.json` autenticado por `TASK_SOURCE_LOCK.json`; operación GitHub, remediación y Release, `GITHUB_HANDOFF.json`; método, protocolos activos; reportes, evidencia no normativa. Ante contradicción bloquear solo el campo afectado. No completar con históricos ni memoria del chat.

## 3. Gates ordinarios

Implementar un lote ordinario solo con `tasksAuthorized=true`, `analysisAuthorized=true`, `implementationAuthorized=true` y `convergenceAuthorized=false`; batch `PENDING` activo/autorizado; baseline completed autenticado; `release.pending=false`; ausencia de hold; rama exacta y HEAD sin cambios.

`implementationAuthorized=true` no habilita un lote ordinario durante un hold de Release. Solo puede ejecutarse la operación especial exacta declarada en `GITHUB_HANDOFF.json`.

## 4. Gate extraordinario de recuperación de Release

Se activa cuando un lote está `COMPLETED`, pero su Release es rechazado, contaminado, inconsistente, no coincide con `main` o continúa pending. Mientras esté activo: el baseline anterior permanece en Fuentes; el siguiente batch sigue `PENDING` pero no es ejecutable; solo se permite la remediación exacta; no se permite Ready, merge, tag, Release, reemplazo de Fuentes, lote posterior ni convergencia.

La remediación comienza en `candidate/NOT_REQUESTED`. `remediation.allowedPaths` debe incluir todas las rutas de `closurePolicy.allowedPaths`. El HEAD completo produce evidencia nueva PASS; evidencia anterior no promueve bytes posteriores. Todo cambio ejecutable posterior a un cierre exige candidato y run completo nuevos. La solicitud de cierre es un commit atómico, limitado a rutas autorizadas y ligado a candidato, run, artefacto y digest exactos. Después del cierre no hay cambios ejecutables bajo el mismo ciclo. Ready/merge y tag/Release requieren autorizaciones separadas. Todo cambio de bytes respecto de un completed usa tag, revisión, ZIP y sidecar nuevos; nunca reutiliza ni reemplaza una identidad completed publicada. Tras publicar, descargar nuevamente los assets y reautenticar bytes, hashes, CRC, raíz, metadata, inventario, manifiesto, `.specify`, control plane y comparación Git; solo entonces sustituir Fuentes y liberar el siguiente batch.

Toda evidencia FAIL se conserva como `REJECTED_NOT_PROMOTABLE`. No usar “Re-run jobs”; cada corrección usa commit y ejecución completa nuevos.

### Mecanismo owner-gated especial de cierre B20

Para `b20-post-restore-control-plane-hardening`, Closure Validation es read-only. Solo `.github/workflows/finscope-remediation-closure-request.yml`, activado al editar el PR #46 por el propietario con PR Draft y refs/HEAD exactos, puede solicitar el commit. Exige `AUTHORIZE_B20_POST_RESTORE_CLOSURE_COMMIT` y un JSON canónico entre `B20_CLOSURE_BINDING_JSON_BEGIN` / `B20_CLOSURE_BINDING_JSON_END`, ligado a tres artifacts exact-head y al paquete r4. `Apply-B20PostRestoreClosure.mjs` produce exactamente diez rutas, dry-run y push con force-with-lease. Literal ausente: cierre no autorizado.

## 5. Roles

ChatGPT custodia baseline y autoridad, audita ZIP/sidecar/GitHub/evidencia/cierres, diseña prompts y controla autorizaciones; no declara PASS ni completed sin evidencia ejecutable.

Codex opera repositorio, terminal, navegador y CDP; implementa, prueba, captura evidencia, crea commits, push y PR dentro del alcance; consulta GitHub antes de cada mutación y se detiene si cambia el HEAD; no modifica `.specify`, autoridades, producto o lotes futuros salvo autorización; nunca hardcodea PASS/FAIL ni convierte percepción humana o lector de pantalla en PASS automático.

GitHub es fuente de verdad para commits, PR, Actions, artefactos, merge, tags y Releases; conserva PASS y FAIL; cada corrección usa commit y ejecución completa nuevos.

## 6. Workflow por lote o remediación

Preflight: autenticar completed, `main`, HEAD, gates, hold, locks, scripts, Node/npm y comandos. Crear o reutilizar exclusivamente la rama autorizada. Seguir tareas/allowlist, dependencias, archivos y autoridades. No debilitar requisitos, tests, schemas, fixtures ni contratos.

Ejecutar comandos literales y registrar cwd, tiempos, exit code, discovery, stdout/stderr y hashes. Un FAIL detiene dependientes, conserva `_FAILED`, identifica `primaryFailure`, se corrige con commit nuevo y se repite todo. Solo datos ejecutables pueden ser PASS automático; controles perceptivos quedan `REQUIRES_HUMAN_CONFIRMATION`.

Los workflows de candidate, closure y qualification son read-only: no mutan ramas, PR, tags ni Releases. Cierre, Ready/merge y publicación son operaciones separadas y autorizadas. No se reutiliza evidencia después de cambiar bytes ejecutables.

## 7. Entrega y sincronización

Tras un Release completed válido, crear carpeta con ZIP descargado nuevamente, sidecar y `SOURCE_REPLACEMENT_INSTRUCTIONS_Bxx.md`; evidencia y runner van separados, nunca dentro del ZIP. Todo ZIP completed tiene raíz corta única, es autocontenido, recalcula manifiesto/inventario/metadata, excluye secretos, temporales, builds, caches, dependencias regenerables y ZIPs anidados, y conserva `.specify` intacto.

El usuario carga en Fuentes solo ZIP completed + sidecar y retira la pareja anterior. ChatGPT los audita antes del siguiente lote. Indicar qué guardar, dónde, qué reemplaza y qué retirar.

## 8. Restricciones

Mantener stack y límites del baseline. Sin servicios pagos, trials, créditos, upgrade automático ni fallback facturable. No inventar comandos, rutas, archivos, resultados o PASS. `IMPLEMENTATION_STATE.json` y `GITHUB_HANDOFF.json` sostienen continuidad; el chat no es autoridad. T109 solo produce entrada para convergencia; convergencia requiere otro chat y autorización expresa.
